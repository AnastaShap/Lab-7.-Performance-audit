## 4. Виправлення

### 4.1. Повторне обчислення рейтингу під час сортування — коміт `c386639`

- **Сценарій:** S2.
- **Метрика:** найдовша взаємодія ___ мс → ___ мс; сума long tasks ___ мс → ___ мс.
- **Причина:** компаратор сортування «Рекомендовані» викликав `tutorScore` для обох елементів при кожному порівнянні: ~38,5 тис. викликів замість 2000, і кожен парсив ~23 дати відгуків. Це повторювалося на кожну літеру в пошуку.
- **Що змінено:** рейтинг рахується один раз на репетитора й береться з кешу (`WeakMap`) у `src/utils/catalog.js`.
- **Доказ:** `report/01-search-before.png` / `report/01-search-after.png`, трейси `report/01-search-*.json`. У Bottom-Up «до» нагорі `weightedRating`; «після» його немає.

### 4.2. Зсуви макета через зображення без розмірів — коміт `d4d7660`

- **Сценарій:** S1.
- **Метрика:** CLS ___ → ___.
- **Причина:** у `<img>` не було `width`/`height`, а в CSS `height: auto`, тож до завантаження картинка мала висоту 0, і після завантаження банер та картки зсували вміст сторінки.
- **Що змінено:** атрибути `width`/`height` у банера та фото в картках — браузер резервує місце за співвідношенням сторін.
- **Доказ:** `report/02-cls-*.png` (доріжка Layout Shifts / аудит Lighthouse).

### 4.3. Важкі зображення затримують LCP — коміт `ea51cee`

- **Сценарій:** S1.
- **Метрика:** LCP ___ с → ___ с; передано ___ МБ → ___ МБ.
- **Причина:** 36 PNG по ~600 КБ (900×900) для карток шириною ~300 px і банер 1,3 МБ завантажувалися одразу й конкурували за канал, тому LCP-зображення (банер) приходило пізно.
- **Що змінено:** WebP потрібних розмірів (`npm run images`, `scripts/optimize-images.mjs`), `srcset`/`sizes`, `loading="lazy"` для карток, `fetchpriority="high"` для банера. Оригінали перенесено в `assets-src/`.
- **Доказ:** `report/03-lcp-*.png` (Lighthouse + Network).

### 4.4. Forced reflow під час скролу — коміт `92475f9`

- **Сценарій:** S3.
- **Метрика:** Layout ___ мс → ___ мс; forced reflow ___ → ___.
- **Причина:** обробник `scroll` у `useBioClamp` для кожної видимої картки чергував запис у DOM (зміна класу) і читання розмірів, тому браузер синхронно перераховував layout сторінки з 2000 карток десятки разів на кожну подію.
- **Що змінено:** спершу всі читання, потім усі записи; обрізаність визначається через `scrollHeight > clientHeight` без зміни класу; оновлення не частіше разу на кадр (`requestAnimationFrame`).
- **Доказ:** `report/04-scroll-*.png` (фіолетові блоки Layout з позначкою Forced reflow «до»).
